## 1. 한 문장 결론

**이 프로젝트는 개인용 AI·반도체 산업 인텔리전스와 의사결정 보조 시스템으로는 충분히 현실적이지만, 미래 업황을 정확히 맞히는 자동 예측 엔진이나 기관급 데이터 서비스를 대체하는 시스템으로 정의하면 현실성이 낮다.**

성공의 기준은 “2028년 실적을 정확히 예언했는가”가 아니라 다음 질문에 빠르고 근거 있게 답할 수 있는가이다.

> 어떤 회사의 Capex·계약·캐파·기술 일정이 바뀌었고, 그 변화가 밸류체인의 어느 기업에 어떤 경로로 전달되며, 기존 시나리오를 왜 수정해야 하는가?

## 2. 현실성 판정

| 목표 수준 | 현실성 | 판단 |
|---|:---:|---|
| 실적·계약·캐파·마일스톤의 로컬 통합 저장 | 높음 | SQLite와 현재 스키마로 구현 가능 |
| 8~21개 핵심 기업의 분기별 비교·검색 | 높음 | 이미 21개 기업, 실적 208건의 기반 존재 |
| 원문 근거가 연결된 개인 리서치 메모리 | 높음 | 출처 모델과 검증 절차를 보강하면 가능 |
| Capex에서 GPU·파운드리·HBM으로 이어지는 관계 시각화 | 중상 | 관계 정의와 중복 계산 방지 규칙이 필요 |
| 병목 변화에 따른 시나리오 비교 | 중상 | 범위·가정·민감도를 명시하면 유용 |
| 자동 뉴스 수집과 중요 변화 알림 | 중간 | 소스별 API·파싱 유지보수가 지속적으로 필요 |
| 2026~2028 업황의 단일 숫자 예측 | 낮음 | 비공개 계약, 가격, 수율, 정책 변수가 커서 과신 위험 |
| Bloomberg·전문 리서치의 완전 대체 | 매우 낮음 | 실시간 데이터, 취재망, 컨센서스 원자료가 없음 |
| 매매 신호의 자동 생성과 수익 보장 | 부적합 | 데이터 지연·편향·모델 위험 때문에 목표에서 제외해야 함 |

따라서 프로젝트는 **예측기보다 증거 기반 판단 시스템**으로 설계해야 한다. 예측은 산출물 중 하나일 수 있지만, 시스템의 정체성이 되어서는 안 된다.

## 3. 왜 현실적으로 구현 가능한가

### 3.1 문제 범위가 제한되어 있다

추적 대상이 21개 기업과 7개 밸류체인 계층으로 고정되어 있다. 모든 금융 데이터를 다루는 범용 플랫폼보다 데이터 사전, 기업 별칭, 핵심 지표, 이벤트 유형을 제한할 수 있어 개인 운영이 가능하다.

### 3.2 기반 구현이 이미 존재한다

현재 DB에는 다음 데이터가 존재한다.

- 기업 마스터 21개
- 분기 실적 208건: 확정 구간 192건, 전망 구간 16건
- 재무 요약 33건
- 계약 10건
- 팹 캐파 11건
- 마일스톤 21건
- 데이터센터 13건

[대시보드](file:///Users/boon/Dropbox/03_code/b_0910_memory_claude/dashboard/index.html), [보고서 생성기](file:///Users/boon/Dropbox/03_code/b_0910_memory_claude/scripts/export_report.py), [로컬 서버](file:///Users/boon/Dropbox/03_code/b_0910_memory_claude/scripts/serve_dashboard.py)도 있으므로 아이디어 단계가 아니라 작동 가능한 프로토타입 단계다.

### 3.3 기술적 난도가 핵심 장애물은 아니다

SQLite, Python, HTML 기반 구조는 한 사람이 유지하기에 적절하다. 핵심 난제는 웹 기술이나 데이터베이스 성능이 아니라 다음 세 가지다.

1. 원문을 지속적으로 수집하는 운영 규율
2. 서로 다른 회계연도·통화·단위를 비교 가능한 형태로 정규화하는 일
3. 사실, 추정, 시나리오를 섞지 않는 데이터 거버넌스

즉, 이 프로젝트의 성공은 코딩량보다 **데이터 신뢰도 관리**에 달려 있다.

## 4. 현실성을 떨어뜨리는 요인

### 4.1 보이지 않는 핵심 변수

HBM 실제 계약 단가, 고객별 배정량, 수율, CoWoS 장기 예약 물량 등은 대부분 완전히 공개되지 않는다. 공개 데이터만으로는 정확한 시장점유율이나 공급량을 단일 숫자로 계산하기 어렵다. 따라서 결과는 `low/base/high` 범위와 신뢰도로 표현해야 한다.

### 4.2 발표 시점과 경제적 귀속 시점의 차이

계약 발표일, Capex 집행일, 장비 반입일, 양산 시작일, 매출 인식일은 서로 다르다. 이들을 하나의 분기에 귀속하면 가짜 인과관계가 생긴다. 각 사건에 다음 시점을 분리해야 한다.

- 발표 또는 관측 시점
- 실제 효력 시작 시점
- 생산능력 반영 시점
- 매출·비용 인식 시점

### 4.3 이중 계산 위험

하이퍼스케일러 Capex 전체를 GPU 지출로 간주하거나, 계약 총액을 한 분기 매출로 처리하면 자본 흐름이 과대 표시된다. 계약 규모, 연간 구매액, 실제 매출 인식액, 공급업체 매출은 서로 다른 지표로 보존해야 한다.

### 4.4 개인 운영의 지속성

21개사 전체를 뉴스 단위로 실시간 추적하면 유지 비용이 급격히 커진다. 현실적인 운영 방식은 핵심 8개사를 깊게 추적하고, 나머지 13개사는 중대한 사건이 있을 때만 갱신하는 방식이다.

권장 핵심 8개사:

- 수요: Microsoft, Amazon, Google, Meta
- 컴퓨팅·생산: NVIDIA, TSMC
- 메모리: SK하이닉스, 삼성전자

## 5. 구현으로 얻는 가장 중요한 가치

### 가치 1. 흩어진 사실을 다시 찾을 수 있는 ‘산업 기억’으로 전환

가장 확실한 가치는 예측 정확도가 아니라 기억의 외부화다. 실적 발표, 계약, 팹 일정, 기술 로드맵을 원문과 함께 축적하면 몇 달 뒤에도 “당시 무엇을 알고 있었는가”를 복원할 수 있다.

구체적 산출:

- 기업·분기별 사실 조회
- 원문과 구조화 값의 양방향 추적
- 전망치 변경 이력
- 과거 판단과 실제 결과 비교

### 가치 2. 밸류체인 간 전달 경로를 한 화면에서 확인

개별 기업 분석만으로는 “수요 증가가 누구의 매출로 전달되는가”를 보기 어렵다. 이 프로젝트는 다음 연결을 하나의 모델로 묶을 수 있다.

`하이퍼스케일러 Capex → 가속기 주문 → 파운드리·패키징 → HBM → 장비 → 데이터센터 전력`

여기서 핵심은 자본 금액을 억지로 완벽하게 배분하는 것이 아니라, 연결의 방향, 지연 시간, 병목, 대체 가능성을 명시하는 것이다.

### 가치 3. 뉴스의 중요도를 구조적으로 판별

모든 뉴스가 같은 가치가 있지 않다. 기존 DB와 비교하면 다음을 구분할 수 있다.

- 이미 알려진 계획의 반복 보도
- 목표 시점의 지연 또는 앞당김
- 금액·캐파·수율의 의미 있는 수정
- 공급자 전환 또는 신규 고객 계약
- 기존 투자 가설을 무효화하는 사건

이는 정보량을 늘리는 가치보다 **뉴스성 소음을 줄이는 가치**가 크다.

### 가치 4. 불확실성을 숨기지 않는 시나리오 사고

단일 전망 대신 전력, 수율, 패키징 캐파, Capex 강도를 변수로 두고 결과 범위를 비교할 수 있다. 구현의 핵심은 정교한 수학 모델이 아니라 가정을 명시하는 것이다.

좋은 시나리오 출력은 다음을 포함한다.

- 입력 가정과 근거
- 기준·상방·하방 범위
- 기업별 영향 방향과 시차
- 결과에 가장 민감한 변수
- 시나리오를 폐기하거나 수정할 관측 조건

### 가치 5. 판단의 복기와 개선

전망 당시의 데이터, 가정, 신뢰도, 결론을 보존하면 결과가 나온 뒤 오류를 분류할 수 있다.

- 데이터가 틀렸는가
- 데이터는 맞았지만 연결 가정이 틀렸는가
- 예상하지 못한 외부 충격이 있었는가
- 방향은 맞았으나 시점이 틀렸는가

이 피드백 루프가 장기간 누적되면 단순 데이터베이스보다 더 가치 있는 **개인 분석 방법론**이 된다.

## 6. 핵심 가치가 아닌 것

프로젝트 범위를 지키기 위해 다음은 핵심 가치에서 제외한다.

- 실시간 주가 단말기
- 모든 기업을 다루는 범용 금융 플랫폼
- 기사 전문을 무제한 수집하는 뉴스 저장소
- 근거 없는 AI 자동 예측
- 복잡해 보이기 위한 대시보드
- 자동 매수·매도 추천

이 기능들은 유지 비용과 책임은 크게 늘리지만 프로젝트의 본질인 장기 자본·기술 흐름 파악에는 기여가 제한적이다.

## 7. 최소 실용 제품의 현실적 범위

### MVP 목표

> 핵심 8개사에 대해 분기 실적, 연간 Capex, 중대 계약, 공급 캐파, 기술 마일스톤을 원문 근거와 함께 조회하고, 변화가 생기면 기존 시나리오의 어느 가정이 바뀌는지 보여준다.

### MVP에 반드시 포함할 것

1. 모든 핵심 레코드의 원문 출처와 검증 상태
2. 실제·전망 구분과 전망 관측일
3. 통화·회계기간 정규화
4. 기업·분기별 변화 비교
5. 3개 병목 변수의 기준·상방·하방 시나리오
6. 변경 이력과 판단 메모
7. 자동 데이터 정합성 검사

### MVP에서 미룰 것

- 21개사 전부의 완전 자동 수집
- 자연어 질의 에이전트
- 정교한 머신러닝 예측
- 실시간 알림
- 다른 산업으로의 확장
- 외부 사용자용 멀티테넌트 서비스

## 8. 운영 부담의 현실적 추정

아래 시간은 현재 코드와 8개 핵심 기업 범위를 전제로 한 계획 추정치이며 실제 측정값은 아니다.

| 단계 | 예상 투입 | 주요 작업 |
|---|---:|---|
| 기반 정비 | 20~40시간 | FK·통화·출처·검증·UPSERT 정비 |
| 핵심 8개사 원문 검증 | 30~60시간 | 과거 핵심 분기와 현재 기준선 검증 |
| 분기 업데이트 | 분기당 8~16시간 | 실적·가이던스·Capex·마일스톤 반영 |
| 평시 유지 | 주당 1~3시간 | 중대 계약·캐파 변경 선별 입력 |
| 시나리오 복기 | 분기당 2~4시간 | 예상과 실제 차이 기록 |

21개사를 모두 동일 깊이로 관리하면 이보다 2~3배 이상 늘어날 수 있다. 따라서 자동화 이전에 추적 깊이를 차등화해야 한다.

## 9. 단계별 성공 기준과 중단 기준

### 1단계: 신뢰 가능한 원장

성공 기준:

- 외래키 위반 0건
- 핵심 레코드의 출처 연결률 100%
- 분석 금액의 USD Billion 정규화 100%
- 전망치에 관측일·신뢰도·범위 존재
- 적재 스크립트 2회 실행 결과 동일

이 기준을 달성하지 못하면 시나리오 엔진 개발을 미룬다.

### 2단계: 반복 사용 가능한 리서치 도구

성공 기준:

- 분기 업데이트가 1~2일 안에 완료됨
- 기업별 변화와 밸류체인 영향을 한 보고서에서 확인 가능
- 원문까지 2회 이하 클릭으로 접근 가능
- 사용자가 실제 판단 과정에서 월 2회 이상 조회

3개월 동안 실제 사용되지 않으면 대시보드 확장보다 입력·조회 흐름을 단순화한다.

### 3단계: 검증 가능한 시나리오 시스템

성공 기준:

- 모든 시나리오에 입력 가정과 폐기 조건 존재
- 이전 전망을 덮어쓰지 않고 보존
- 분기마다 오차 원인을 복기
- 최소 4개 분기 누적 후 방향·시점·범위 정확도를 별도로 평가

4개 분기 전에는 모델의 예측력을 주장하지 않는다.

## 10. 투자 대비 가치 판단

이 프로젝트가 가치 있는 경우:

- 사용자가 AI·반도체 밸류체인을 수년간 지속적으로 추적할 계획이 있다.
- 외부 리서치를 읽고 끝내지 않고 자신의 가설과 판단을 축적하고 싶다.
- 매수·매도 신호보다 산업 구조와 변화의 근거를 중요하게 본다.
- 매주 소량, 매 분기 집중적으로 데이터를 관리할 의향이 있다.

가치가 낮은 경우:

- 단기간에 종목 추천만 얻고 싶다.
- 원문 검증과 정기 갱신에 시간을 쓸 수 없다.
- 실시간 시세·뉴스 속도가 가장 중요하다.
- 예측 결과를 확률이 아니라 확정 답으로 기대한다.

## 11. 최종 권고

프로젝트는 계속 구현할 가치가 있다. 다만 목표를 다음처럼 재정의하는 것이 현실적이다.

> Memory Claude는 미래를 맞히는 기계가 아니라, AI·반도체 밸류체인의 중요한 변화를 원문 근거와 시간축 위에 축적하고, 자본·생산능력·기술의 연결을 비교하며, 사용자의 판단과 가설을 지속적으로 검증하는 개인 인텔리전스 시스템이다.

앞으로의 개발 우선순위는 기능 수가 아니라 **신뢰 가능한 데이터 → 빠른 갱신 → 관계 분석 → 시나리오 복기**가 되어야 한다. 이 순서를 지키면 작은 로컬 시스템으로도 실제 의사결정 품질을 높이는 고유한 자산이 된다. 반대로 출처가 불분명한 숫자를 늘리고 자동 예측부터 확장하면 대시보드는 화려해져도 핵심 가치는 생기지 않는다.

## 12. 평가의 한계

이 평가는 현재 저장소 내부 구현과 DB 상태를 기준으로 한 현실성 판단이다. 외부 시장 데이터, 상용 서비스 가격, 개별 기업의 최신 공시를 새로 검증하지 않았으며, 여기에 제시한 운영 시간은 프로젝트 범위와 현재 코드량을 바탕으로 한 계획 추정치다.
